CAIRNAI: PERSONAL AI WORKSPACE
MASTER PROJECT EXECUTION SPECIFICATION

PROJECT INTENT

Build a production-oriented personal AI workspace that acts as my own persistent LLM client.

The motivation is simple: I do not want to repeatedly open ChatGPT, Claude, Gemini, or other web interfaces just to have a conversation with an LLM.

I want one application that stays available as my personal AI interface and connects to LLMs through my local 9Router instance.

9Router is a free, open-source local proxy and smart gateway that exposes one unified endpoint in front of many upstream AI providers. See section 0 for what that means for the design.

This project will be open sourced. Anyone must be able to clone it, add their own API key for the provider they use, choose any model that provider offers, and start chatting. 9Router is my default and recommended gateway. It is not the only supported provider. See section 0.

Speed is a core requirement. When I use CairnAI, the application itself must never feel slow. I do not want to observe any latency that the app adds. See section 27.

Modular decomposition is mandatory. The work is done in small modules, one at a time, and in no other way. There are no exceptions. See section 1A.

I also want to see progress at any time. Claude Code maintains a PROGRESS.md file in the repository root that shows exactly how much is done, and where I can write instructions. See section 2A.

The product should eventually feel less like a "ChatGPT clone" and more like a personal AI operating workspace.

Core product statement:

"A personal AI workspace with multi-model routing, persistent conversations, document RAG, streaming inference, file interaction, session-based history, local project/workspace storage, and tool/MCP integration."

This is intended to become a serious portfolio project demonstrating both software engineering and AI engineering.

WHAT 9ROUTER IS AND WHAT THAT MEANS FOR THE DESIGN

9Router is a free, open-source (MIT-licensed) local proxy and smart gateway
(project: github.com/decolua/9router). It sits between a client and many upstream
AI providers and exposes one unified endpoint. It was built mainly for AI coding
tools (Claude Code, Cursor, Cline, Copilot and similar). My application is a
different kind of client of the same gateway: a general personal AI workspace.

Understood from the project's documentation and community sources, NOT yet
verified against my running instance:

- It runs locally as a proxy with a web dashboard. A commonly reported default is
  http://localhost:20128 with the API under /v1.
- The unified endpoint is reported to be OpenAI-compatible and to translate
  between upstream provider formats.
- Upstream provider accounts, API keys and OAuth connections are configured
  INSIDE 9Router (its dashboard), not in my application.
- It supports "combos": virtual model IDs that group several models with
  automatic fallback. Fallback, quota tracking and account round-robin happen
  inside 9Router.
- It can optionally require an API key from clients.
- Beyond chat it is reported to expose other endpoints, such as embeddings.
  Exact availability depends on version and configured providers.
- The number of supported providers and models differs between sources and
  changes between versions. Do not hardcode or advertise a number.

DESIGN CONSEQUENCES

1. For a 9Router profile, my app holds only what it needs to talk to 9Router:
   a base URL and, if required, a 9Router API key. Upstream provider keys stay
   inside 9Router. My app must never ask for, copy, store or log them. For other
   provider profiles the app holds that provider's own API key under the rules
   in the providers section below.
2. 9Router owns provider-level routing and fallback for 9Router profiles. My
   app must NOT reimplement provider fallback, quota tracking or account
   rotation. In this project "multi-model routing" means: discover the models
   each configured provider offers (including 9Router combos), let me select
   them (default, per-session, per-conversation, mid-session), and record which
   model was used.
3. Because 9Router and many other providers expose OpenAI-compatible endpoints,
   one generic OpenAI-compatible adapter can serve 9Router and many others. The
   gateway/provider interface (see section 9) is the boundary. Add a native
   adapter only when a provider's API is not OpenAI-compatible, and only as
   listed in the providers section below. Do not add layers beyond that.
4. Model metadata (context window, tool support, multimodal support) may be
   missing or incomplete in the model listing. Keep an app-level metadata layer
   with safe defaults and user overrides. Do not assume the gateway provides it.
5. Combos can hide which upstream model actually answered. Record what the
   gateway reports where available. Keep the requested model ID and the actual
   responding model as separate fields if both are available.
6. The gateway is local. The default deployment is local-first: backend and
   9Router on the same machine. If the app is ever deployed remotely it cannot
   reach a localhost 9Router unless deliberately exposed. Document this in the
   deployment architecture.
7. The frontend never calls 9Router or any other provider directly. Only the backend does.
8. 9Router's own security posture matters. Verify that its dashboard password
   has been changed from any default and that its endpoint is not exposed beyond
   localhost without an API key. Document this in docs/08-SECURITY.md.
9. Gateway health is a first-class state. 9Router not running, unreachable, no
   providers configured, and providers exhausted or rate-limited are distinct,
   user-visible error states, not one generic failure.
10. Some providers routed through 9Router may rely on subscription or OAuth
    sessions, free tiers with limits, or terms that restrict proxy use. Managing
    that is my responsibility as the operator, but the BRD Risks section must
    record upstream availability, quota limits and provider-terms risk.

VERIFY IN PHASE 0 (against my running instance and its documentation, not memory)

PROVIDERS, MODELS AND API KEYS (OPEN-SOURCE REQUIREMENT)

This project will be open sourced. Anyone must be able to clone it, add their
own API key for the provider they use, pick any model that provider offers, and
chat. 9Router is my default and recommended gateway. It is not the only one.

Provider profiles

- A provider profile has: id, display name, adapter type, base URL, a reference
  to its stored credential (never the raw key inside the profile record),
  optional extra headers, an enabled flag, and optional per-model metadata
  overrides.
- Profiles are added, edited, tested, disabled and removed at runtime from the
  Settings dialog. No code change and no restart.
- Any number of profiles can exist. One is marked default.
- A fresh install has no profile configured. First run shows a clear empty state
  that leads to adding one. Provide presets that only prefill the form (adapter
  type and a verified base URL): 9Router, generic OpenAI-compatible, Anthropic,
  Google Gemini. Presets never contain keys.
- Adapter types, implemented in this order:
  1. openai-compatible: the widely used chat-completions style API with
     streaming and, where available, model listing. Serves 9Router and any
     hosted or self-hosted provider that exposes this style, including local
     runners on localhost.
  2. anthropic: that provider's native messages API.
  3. google-gemini: that provider's native API.
  Verify each API contract against that provider's current official
  documentation in Phase 0. Do not rely on memory. Further adapters go behind
  the same interface.
- Internal adapter interface: list models, stream chat, report capabilities,
  test connection, normalize errors. Provider-specific errors are normalized
  into the app's distinct error states: unreachable, unauthorized, rate
  limited, quota exhausted, model not found, malformed stream, timeout.
- Only claim support for a provider that has a passing integration test or a
  documented manual verification. Everything else is listed as untested in
  docs/13-PROVIDERS.md and in the README.

Models

- Models for a profile come from its model-listing endpoint when it has one.
  Cache the list and refresh it in the background (see section 27).
- If a provider has no listing, or an incomplete one, I can add a model ID
  manually. Manually added models persist per profile.
- A model is always identified by the pair (profile id, model id). Two
  providers can expose the same model ID.
- I can change the model at any time: the app default, per session, and
  between messages inside a session. Changing it never loses or rewrites
  history. The context builder adapts to the new model's context window and
  capabilities.
- Capability metadata (context window, tool calling, vision) comes from the
  provider when it reports it, otherwise from my overrides, otherwise it is
  unknown. Unknown is never assumed to be supported.
- Each assistant message records the profile, the requested model and, when
  reported, the model that actually answered.

API keys and secrets (safe to open source)

- Keys are entered in the Settings dialog or supplied through environment
  variables. Only the backend holds them. The UI never shows a saved key again.
- Storage is decided by ADR. Prefer the operating system credential store. If
  it is unavailable, use a local file outside the repository with owner-only
  permissions. Never plain text in the workspace database or in exports.
- The repository ships .env.example with placeholder names only, a .gitignore
  that covers secrets and the local workspace, and an automated secret scan
  (pre-commit or CI) so a real key cannot be committed.
- Workspace export and backup exclude keys.
- A key is sent only to the base URL of the profile it belongs to. Do not
  follow a redirect to a different host with the auth header attached.
- Validate base URLs (http or https only). Allow localhost and private
  addresses because local runners need them. Warn when a non-local host uses
  plain http.
- Never log keys. Redact them from error messages.

Configuration

- Non-secret settings (profiles without keys, default model, theme) live in the
  local workspace settings. Secrets follow the rules above.
- No key rotation, load balancing or failover inside my app for direct provider
  profiles. Leave an extension point and document it. For 9Router profiles,
  9Router does that.

============================================================
1A. MODULAR WORKING METHOD
============================================================

Build CairnAI as a set of small modules with clear boundaries, and build them
one at a time.

Why: an AI agent cannot build everything at once. Quality drops and context is
wasted when it tries. Small modules are easier to test, review and replace.

MANDATORY

Modular decomposition is the only permitted way of working on this project. It
is not a preference and it has no exceptions.

- Do not generate the whole application, or several modules, in one step.
- Do not write implementation code for a module before its interface is written
  down (in the architecture document or the module's README).
- Before every task, write a short task brief in PROGRESS.md: the module, the
  slice, the interface it uses, the tests, and the files it will touch. Start
  coding only after that.
- A change that touches the internals of more than one module must be split into
  module-sized changes. The only allowed multi-module change is a planned
  integration slice (rule 9), and even that goes through public interfaces.
- If a task cannot be split into module-sized pieces, stop and split it first.
  Do not proceed with an oversized task.
- Size guideline: a slice is about 400 changed lines or fewer, excluding tests
  and generated files. A larger slice needs a written reason in PROGRESS.md.
- If a violation happens (a big-bang change, or reaching into another module's
  internals), stop, split or revert it, and record it in PROGRESS.md before
  continuing.
- Where practical, one module per work session.
- This rule wins over speed. Never skip it to finish faster.

MODULE MAP

Phase 0 defines the module map in docs/01-ARCHITECTURE.md: for each module its
name, responsibility, public interface, dependencies and folder.

A starting point, to be adjusted in Phase 0:

- workspace and storage
- sessions, conversations and messages
- provider gateway (adapters, profiles, model catalog)
- streaming
- files
- document processing and RAG
- MCP and tools
- skills
- context builder
- settings and secrets
- UI shell and UI components (sidebar, composer, drawer)
- observability and the performance harness

RULES

1. One module at a time. Finish and verify a module before starting another that
   depends on it.
2. Define the module's public interface first (types and contract), write it in
   the architecture document or the module's README, then implement behind it.
3. Modules talk only through public interfaces. No reaching into another
   module's internals. No circular dependencies. Dependencies point one way:
   UI, then application services, then modules, then storage and gateways.
   Enforce this with a dependency check if the chosen stack supports one.
4. Each module has its own folder, a short README (purpose, interface,
   dependencies, how to test), and its own tests. Modules it depends on are
   replaced by stubs or mocks so it can be tested alone.
5. Keep files small and single-purpose. Split a file that does several jobs. As a
   guideline, avoid files over about 300 lines and document any exception.
6. Every task is module-sized: one module, or one clear slice of a module, small
   enough to review as a single change. Commit each finished slice with a clear
   message.
7. Hot-path modules (streaming, the send path, the context builder, message
   rendering) are built and benchmarked on their own before integration
   (section 27).
8. The provider gateway, storage, vector store and MCP client sit behind
   interfaces, so any of them can be replaced without touching the rest.
9. After modules pass alone, integrate a thin vertical slice early in Phase 2:
   one message sent, streamed, saved and shown end to end. Then widen from
   there. This exposes integration problems early.
10. Track module status in MEMORY.md and PROGRESS.md: not started,
    interface defined, implemented, tested, integrated.
11. Do not create modules for deferred features (section 28). Leave extension
    points only.

Modules are boundaries with a purpose, not layers for their own sake. Do not
create a module or an interface that has one caller and no reason to be
replaced, except the boundaries listed above.

3. RULES (RULES.md, referenced from CLAUDE.md)

What it does: sets boundaries for the AI. It says which libraries to use or
avoid, how to handle errors, and what the AI should and should not do.

Create it in Phase 0 after the technology decisions, and before implementation.
Write it short, imperative and specific. Build it from this specification and
from design.md. Do not invent rules that contradict either. Seed it with:

- Stack and dependencies: use only the stack chosen in docs/03-TECHNICAL-DECISIONS.md.
  Adding a dependency needs a recorded decision. Prefer fewer dependencies.
  A dependency must be actively maintained and license-compatible with open
  sourcing. List the libraries to avoid, each with its reason.
- Error handling: use the normalized provider error states. Never swallow an
  error. Never show a generic "something went wrong". Every user-visible error
  has a plain message and an action. Never leak keys or file contents into logs
  or messages.
- Security: keys stay in the backend. The frontend never calls a provider.
  Uploaded documents and tool output are untrusted. Validate files and paths.
  No secrets in commits.
- Performance: the hot-path budgets in section 27. No buffering on the stream
  path. No blocking work on the send path.
- Design and copy: follow design.md. Its bans in section 0.2 apply to all UI,
  docs and README text (no purple gradients, no pill shapes, no fake metrics,
  no emoji icons, no em dashes, and the rest of that list).
- Scope: build only the current phase. Do not build deferred features. The only
  routes are /, /privacy and /terms.
- Verification: do not claim a task is done without running the tests. Do not
  claim provider support without a test. Do not invent API behaviour, check the
  official documentation.
- Modules (mandatory): work in modular decomposition only (section 1A). One module at a time. Define
  the interface first. Talk to other modules only through their public
  interfaces. Keep files small and single-purpose. Give each module its own
  README and tests.
- Working style: read MEMORY.md first. Do not re-read the whole codebase. Make
  the smallest change that solves the problem. Do not touch unrelated files.
  Ask before destructive actions (deleting data, force pushes, mass rewrites).
  Do not edit design.md without asking. Update the docs together with the code, and
  update PROGRESS.md at the end of every session.

14A. SKILLS
============================================================

Skills make repeated work easier and keep token use low.

WHAT A SKILL IS

A skill is a folder containing a SKILL.md file: a short name, a one-line
description, and instructions the model follows for one kind of task. Optional
supporting files (templates, reference notes) can sit beside it.

Skills are plain text. In this version a skill cannot contain or run code.
Anything that needs actions goes through MCP tools and their permission prompts.

Verify the current SKILL.md convention (front matter with name and description)
against Anthropic's published documentation in Phase 0. Follow it where it fits.
Do not claim full compatibility with other tools unless it was tested.

WHERE SKILLS LIVE

- Workspace skills: a skills/ folder inside the local workspace. Available in
  that workspace only.
- Global skills: a skills/ folder in the application data folder. Available in
  every workspace.
- Starter skills: shipped in the repository under skills/starter/ and copied in
  on first run. I can edit or delete them.
- The app indexes skills in the background and caches the index by file hash.
  It never scans skill folders on the send path.

HOW SKILLS SAVE TOKENS (progressive loading)

Level 1, always in context: only the name and description of each enabled skill
(description limit about 200 characters, a few dozen tokens per skill).
Level 2, loaded on demand: the full SKILL.md body enters the context only when
the skill is activated.
Level 3, loaded only if needed: supporting files, read only when the skill body
points to one and the model or I ask for it.

Activation:

- By me: type / in the composer and pick a skill, or use the Skills tab.
- By the model: through a built-in load_skill tool, only when the selected model
  supports tool calling. If it does not, only my explicit activation works.
- Never inject a skill body just because a keyword matched. The app may suggest
  a skill, and I confirm.
- An activated skill stays active for that session until I deactivate it. It is
  shown as a chip.

Limits (defaults, adjust after measurement):

- description up to about 200 characters
- up to 20 enabled skills in the index. Above that, ask me to disable some.
- body: warn above about 2,000 tokens, reject above about 8,000 tokens unless
  I override
- show the estimated token cost of every skill (index cost and body cost) in the
  UI, and include activated skills in the context meter

Prompt order: keep system instructions, the skill index and activated skills in
a stable order at the start of the request, so provider-side prompt caching can
help where a provider offers it. Do not rely on that.

Do not claim token savings without measuring them. Record the measured index and
body overhead in docs/12-PERFORMANCE.md.

PROVIDER INDEPENDENCE

Skills are injected as text, so they work with any provider and model. Only the
model-driven load_skill path depends on tool-calling support. Record that in the
model capability metadata (section 0).

SESSIONS

Active skills are stored per session and do not leak into other sessions. New
sessions start with none active, except a default set I choose in Settings.

COMPACT (CONTEXT SAVER)

Provide a Compact action for long sessions.

- It asks the current model, using the compact-context skill, to summarize the
  older part of the conversation into a short brief.
- The summary is stored as a message marked as a summary.
- Older messages stay visible in the session history and stay in the database,
  but the context builder sends the summary instead of them.
- Show the estimated token count before and after. I can undo it.
- Never compact automatically without telling me.

STARTER SKILLS

Ship these as plain SKILL.md files. Each body stays under about 300 tokens.

1. concise-answers: answer directly, no preamble or recap, short by default,
   expand on request. Saves output tokens.
2. compact-context: how to summarize a conversation into a brief that keeps
   decisions, open questions, names and constraints. Used by Compact.
3. document-qa: answer only from retrieved passages, cite them, say clearly when
   the documents do not contain the answer, quote sparingly.
4. summarize-document: a short structured summary with key points, decisions and
   open questions.
5. code-review: a focused checklist (correctness, security, edge cases, tests)
   and a brief, prioritized output.
6. create-skill: helps me write a new skill from a description, with a short
   description and a lean body.

Each starter skill must be verified manually against at least one configured
provider before it is described as working.

SECURITY

- Skills I write are trusted as my own instructions. Skills imported from
  elsewhere are untrusted text: show the full content before enabling, and never
  enable on import automatically.
- A skill cannot change tool permissions, provider settings or app settings, and
  cannot approve a tool call. Tool calls always go through the permission
  prompts in section 14.
- Skill text does not override the application's own safety rules or the
  untrusted labelling of documents and tool output.
- Supporting-file paths must resolve inside the skill folder. Reject path
  traversal and symlinks that leave it. Limit file sizes and the number of files.
- Never log full skill content.

NOT IN SCOPE NOW

Plugins that bundle skills, MCP servers and code. Leave the extension point
noted in section 28.

============================================================
27. PERFORMANCE AND PERCEIVED LATENCY
============================================================

GOAL

When I use CairnAI, the application itself must never feel slow. I do not want
to observe any latency that the app adds.

What the app cannot control: network time and model inference time at the
provider. Do not claim "zero latency" anywhere. Claim only numbers that were
measured, and state the test setup.

Design for speed from the start. Architecture-level choices (process layout,
streaming path, storage, rendering approach) are made for latency up front.
Micro-optimizations are guided by measurement.

Do not trade correctness or security for speed.

HOT PATHS (these must feel instant)

1. opening the app
2. pressing send until the first token is on screen
3. streaming render
4. switching sessions
5. typing in the composer
6. opening the model picker
7. uploading a file (the UI stays responsive)
8. scrolling long conversations

BUDGETS

These are targets. Validate them in Phase 0 and Phase 7 and record the actual
measurements in docs/12-PERFORMANCE.md. If a target cannot be met, document the
measured value and the reason in an ADR.

- Keypress or click to visible feedback: under 100 ms. Typing: within one frame (16 ms).
- App-added time between pressing send and the request leaving the machine: under 20 ms.
- App-added time per streamed chunk (chunk received to pixels updated): under one frame.
- First-token overhead compared with calling the provider directly with the same request: under 30 ms.
- Switching to an already loaded session: under 100 ms. Any session, even with a long history: under 200 ms.
- Cold start to interactive UI: under 2 s. Warm start: under 1 s.
- Opening the model picker: under 50 ms, from cache.
- Activating or deactivating a skill: under 50 ms. The skill index is cached and never rebuilt on the send path.
- Streaming a long response that contains code blocks: sustained 60 frames per second, with no visible stutter.

Measure app overhead against a local mock streaming provider so the results do
not depend on the network. Also record numbers against at least one real
provider profile.

ARCHITECTURE REQUIREMENTS

Streaming path

1. Pass chunks through as they arrive. Forward each provider chunk to the
   frontend immediately with an explicit flush. No buffering by middleware,
   compression or proxies on event streams.
2. Reuse connections (keep-alive, connection pooling, HTTP/2 where the provider
   supports it). Warm the connection to the default provider at startup and
   when the composer gains focus.
3. Stop cancels the upstream request and stops rendering within a frame.

Send path

4. Before the request leaves, do only what changes the request. Persisting the
   user message, title generation, logging and embedding never delay the
   provider request. Persist the user message in parallel with the request, and
   mark the turn complete only after it is durable.
5. Buffer assistant tokens in memory and flush them to storage in batches and on
   completion, cancel or error. A crash must leave a recoverable partial message.
6. Context building is incremental and cached: cache token counts per message,
   keep the active session's recent messages in memory, and never re-read or
   re-tokenize the full history every turn.
7. Retrieval runs only when the mode needs it, in parallel with other request
   preparation, under a hard time budget (local retrieval typically under
   100 ms). If it exceeds the budget, tell me it was skipped. Do not silently
   answer without the documents.
8. Optimistic UI: the user message appears instantly and the assistant
   placeholder appears immediately.

Background work

9. File parsing, chunking and embedding run in background workers with
   progress. Chat and UI never wait on them. Skip unchanged files using a
   content hash. Lazy-load heavy parsers.
10. Initialize MCP servers, parsers and embedding models lazily or during idle
    time, never before the UI is interactive.

Storage

11. Use a local embedded database with write-ahead logging, indexes for the hot
    queries (sessions by recency, messages by session and order), prepared
    statements, no N+1 queries, windowed loading of long histories, and an
    index-based search for sessions and messages.

Frontend

12. Virtualize the message list and the session list.
13. Render streaming text incrementally. Batch DOM updates to at most one per
    animation frame. Memoize completed blocks. Do not re-parse or re-render the
    whole message for every token. Defer or incrementally apply syntax
    highlighting.
14. Keep the initial bundle small. Code-split the context drawer, settings and
    heavy libraries. Keep main-thread tasks under 50 ms and move heavy work to
    workers.
15. Cache model lists per provider profile (stale-while-revalidate). No network
    call blocks opening the model picker.

Process layout

16. One local backend process with the frontend served locally. No unnecessary
    hops or serialization layers between UI, backend and provider. No
    microservices.
17. Work in one session never slows another session or the UI.

Technology choices

18. Every technology ADR (backend, frontend, database, streaming protocol) must
    include the latency reasoning for the streaming path, storage and rendering.
    Do not pick a stack because it is fashionable.

Measurement

19. Instrument the hot path with timestamps: send pressed, request dispatched,
    first byte from provider, first token rendered, stream complete. Expose them
    in a developer view or logs. Never log message content.
20. Provide a benchmark script and automated budget checks so a regression is
    caught.
21. Record results in docs/12-PERFORMANCE.md. README performance claims must be
    measured numbers with the test setup stated.

Also avoid sending unnecessary historical or context data to the LLM.
